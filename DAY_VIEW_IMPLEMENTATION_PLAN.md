# План переработки выбранного дня

Дата: 6 октября 2026. Репозиторий: `/path/to/project`. Статус: план готов к реализации; код приложения в ходе подготовки не менялся.

## 1. Решение

Экран дня остаётся частью календаря `/`: тёмно-зелёный фон, песочный акцент, Manrope, DM Mono, тонкие разделители и существующие SVG. Основное действие — записать заработок за выбранную дату. Сразу видны четыре показателя: «Заработано», «В пути», «Получено», «Потрачено». Кассовый итог остаётся вторичной строкой с явной формулой.

Доход сохраняется существующим `POST /api/income` в статусе `EARNED`. Показатель «В пути» включает `EARNED + IN_TRANSIT`: это уже прямо определено в `DOMAIN_RULES.md`, RULE-FS2, и согласуется с RULE-I2. Исправить два расходящихся агрегата, а не менять статус записи ради интерфейса. Доступный и свободный баланс от такого сохранения не растут.

Скриншот трат и ИИ — два небольших информационных блока ниже рабочего содержимого. Без upload, распознавания, вызовов модели, фиктивного ранга дня, неработающих кнопок и обещания срока выпуска.

## 3. Точный смысл денег и дат

Все значения API и вычислений — целые копейки. Форматирование денег выполняется только для UI. Показатели дня — факты по указанным датам плюс текущий статус соответствующих записей, НЕ исторический снимок «на конец того дня».

| Показатель | Источник и правило | Текст пояснения |
| --- | --- | --- |
| Заработано | `earnedAt` попадает на выбранный день, status != CANCELLED, включая RECEIVED и DELAYED | «За работу в этот день» |
| В пути | `earnedAt` попадает на выбранный день, status ∈ {EARNED, IN_TRANSIT}, новое `inTransitIncome` | «Из заработанного за этот день ещё не получено. Задержанные выплаты учитываются отдельно в ожиданиях» |
| Получено | status=RECEIVED, `receivedAt` попадает на выбранный день | «Поступило в этот день, в том числе за прошлую работу» |
| Потрачено | Расходы по `expenseDate` выбранного дня | «Фактические расходы; запланированные платежи сюда не входят» |
| Получено − потрачено | Только `receivedIncome - expenses`, существующий realizedNet | «Движение денег за день»; это не весь доступный баланс |
| Ожидаемые выплаты (в деталях) | Существующее `expectedIncome`: EARNED/IN_TRANSIT/DELAYED, дата expectedAt, либо earnedAt, если срок не задан | «По указанной дате выплаты; если срок не задан — по дате заработка» |

«Заработано» и «Получено» не складывать: одна запись может присутствовать в обоих показателях. «В пути» — часть заработанного выбранного дня, а глобальное «В пути» на главной — сумма по всем дням. После получения денег старый день сохраняет заработок, но его текущая сумма «В пути» уменьшается. Формула `заработано = получено + в пути` для дня неверна: даты различны, есть DELAYED.

DELAYED сознательно не добавляется в «В пути»: RULE-FS2 перечисляет EARNED/IN_TRANSIT, а правило планирования RULE-PC4 включает DELAYED в ожидаемые поступления. DELAYED остаётся в заработанном и в существующей строке ожидаемых выплат; не показывать ложный текст «все деньги получены», если inTransitIncome=0. Не вводить новую политику просрочки или автоматические переходы статусов. CANCELLED исключить из заработанного календаря, как уже сделано в dashboard.

### Почему не переводить всё в IN_TRANSIT

`POST /api/income` → `createIncome` создаёт `EARNED`, что проверяется тестами. `updateIncomeStatus` существует в domain service, но публичного status-route сейчас нет. Ни принудительная смена default, ни цепочка POST → PATCH не нужны: ввод «заработал» не подтверждает отправку выплаты. Сохраняем граф переходов RULE-I3 и terminal RECEIVED/CANCELLED.

`getIncomeInTransit` сейчас выбирает только IN_TRANSIT. Важно: финансовая сводка НЕ вызывает эту функцию — `getFinancialSnapshot` в `envelopeService.ts` содержит второй независимый SQL с тем же ограничением. Исправить ОБА места на EARNED/IN_TRANSIT, иначе главная не обновится даже при исправленном income service. Достаточно существующего `inArray`/SQL-предиката, без нового repository/service слоя. Тесты должны подтверждать равенство этих агрегатов на одном наборе записей.

## 6. Сценарий записи заработка

1. Пользователь нажимает день на `/`. Заголовок и форма привязаны к одному date-only ключу `YYYY-MM-DD`. Выбор соседнего дня, включая месяц/год, обновляет year/month и загружает нужные events. На время нового GET старый массив не считается данными нового месяца. Использовать abort + проверку актуальности результата; запоздалый ответ не должен заменить выбранный месяц.
2. Форма показывает «Заработок за 6 октября», одно поле «Сумма, ₽» и подсказку о неполученных деньгах. Источник сохраняется как «Работа». Дата уже выбрана, повторный date picker не нужен; expectedAt не выдумывается и в первом этапе не вводится. Каждое подтверждение добавляет отдельную запись, не заменяет дневной итог. Короткая подсказка после первой записи: «Можно добавить ещё один заработок».
3. Для будущей относительно локального сегодня даты метрики доступны, но форма записи фактически заработанного заменяется текстом «Заработок можно записать за сегодня или прошедший день». Это ограничение быстрого сценария; существующий generic API не превращать в API планируемого дохода.
4. `inputMode=decimal`, видимый label, ввод принимает запятую или точку и максимум две дробные цифры. Trim краёв; reject пустое, ноль, минус, экспоненту, мусор, несколько разделителей, >2 дробных знаков и unsafe integer. Не использовать `parseFloat`, который принимает `123abc`, и не округлять лишние копейки. Минимальный проверяемый parser можно добавить в существующий `src/lib/money/index.ts`: разобрать целую/дробную часть строки в целые копейки, проверить safe integer; использовать его из формы, без нового money SDK. `money.validate` сейчас проверяет integer, но не safe integer — учесть это на границе POST (и не менять молча поведение всех money helpers).
5. Отправить ровно один POST с `{amountKopecks, source:'Работа', earnedAt: selectedDate + 'T00:00:00.000Z'}`. `expectedAt`, status, receivedAt, userId в payload не передавать. ISO здесь кодирует существующую календарную UTC-date convention, а не реальное время смены. Сервер остаётся источником статуса и владельца записи.
6. 201 подтверждает сохранение EARNED. Очистить amount только после подтверждения, показать inline `role=status`, обновить календарь выбранного месяца и `/api/dashboard`. Не увеличивать деньги оптимистически на клиенте. Вынести минимальную reload-функцию/счётчик в HomePage, а не внедрять query cache библиотеку. Сбой каждого GET учитывать отдельно.
7. После успешных GET заработок и inTransitIncome выбранного дня выросли на сумму, глобальное incomeInTransit тоже выросло, receivedIncome/availableCash/discretionary/realizedNet не изменились. Возврат показывает актуальный календарь того месяца, к которому относится выбранная дата. Возвращать фокус на выбранную календарную кнопку; при открытии дня фокус на заголовок, не в input (не открывать клавиатуру автоматически).
8. При ошибке POST оставить сумму; понятная validation error разрешает исправление и повтор. При потере ответа статус записи неизвестен: не делать автоматический POST retry и не утверждать «не сохранено». Сообщить «Не удалось подтвердить сохранение. Проверьте обновлённые показатели перед повторной записью», предложить обновить GET. Disabled/in-flight guard предотвращает двойной тап, но НЕ даёт exactly-once при потерянном ответе. Серверную идемпотентность не изображать реализованной; её надёжная гарантия потребует отдельного решения хранения ключа.
9. При переходе на другую дату/назад с непустым draft не переносить сумму незаметно. Простейший вариант — явное подтверждение сброса через native confirm; при отмене остаёмся на дне. Во время отправки эти переходы блокируются до завершения POST. Draft не сохраняется в persistent storage; браузерная перезагрузка не обещает его восстановления.

Переработать существующий, сейчас нигде не используемый `IncomeForm` под этот конкретный сценарий: минимальные props выбранной даты, privacy и callback сохранения/состояния отправки, необходимые родителю для навигации. Состояние формы должно сбрасываться осознанно при смене даты. Не строить универсальный form builder, modal manager или несколько вариантов одной формы «на будущее».

## 9. Инварианты и риски

- RULE-M1/M2/M3: integer kopecks, точный разбор десятичного ввода, без молчаливого округления третьего знака; денежные операции через существующие utilities.
- RULE-I1/I2: EARNED/IN_TRANSIT/DELAYED не пополняют spendable balance; receivedAt и RECEIVED необходимы для фактического поступления.
- RULE-I3/I4: сохранить разрешённые переходы, terminal статусы и запрет отмены RECEIVED. CANCELLED нигде не увеличивает earned/received/transit/expected.
- Защищённые средства, доступность распределения, расходы и выплаты долгов не пересчитывать на клиенте; корректировка transit не меняет HARD/protected/discretionary.
- Все запросы доходов/агрегатов сохраняют userId filter. В текущих routes placeholder USER_ID; эта задача не реализует multi-user auth, не принимает владельца из body и не утверждает, что placeholder обеспечивает полноценную аутентификацию. Сохранить существующие security hooks/origin checks, если они появились к моменту реализации.
- Date-only navigation ограничена поддерживаемыми API годами 2000–2100; крайние стрелки не ведут на заведомо невалидный запрос. Заголовок, payload и GET month всегда относятся к одной дате. Проверить 31 декабря/1 января и 29 февраля.
- В `calendarService` сейчас границы выборки expenses построены в локальной зоне сервера, конец месяца до 23:59:59 без последних миллисекунд. Для достоверных метрик дня перейти на единый UTC полуинтервал `[начало месяца, начало следующего)` для timestamp-полей, соответствующий имеющейся UTC-date агрегации, и проверить конец месяца. Не вводить полноценную user-timezone миграцию в этой задаче.
- После успешного POST ошибка GET не должна позволять невольно продублировать ту же запись. Сетевой timeout POST не равен rollback. Явно описать предел защиты повторов.
- `tests/unit/dashboard/dashboardService.test.ts` сейчас ожидает transit=40000 при EARNED=25000. Новое правильное ожидание по RULE-FS2 — 65000; обновить с объясняющим тестом, не просто «подогнать» числа. Проверить downstream planning/AI snapshot tests: transit там информационный, не spendable.
- `tests/e2e/navigation.spec.ts` содержит старые ожидания «Финансы», «Главная», отдельного calendar route через nav. Исправлять только устаревшие ожидания, затронутые актуальным календарём; не удалить проверки для зелёного результата.
