ЗАДАЧА: РЕАЛИЗОВАТЬ НОВЫЙ ГЛАВНЫЙ ЭКРАН PERSONAL FINANCE OS

Ты работаешь не над концептом и не над отдельным mockup.

Ты работаешь непосредственно внутри существующего проекта Personal Finance OS.

Твоя задача:

«Полностью переработать UI/UX главного экрана приложения в соответствии со спецификацией ниже, сохранив существующую бизнес-логику и сделав конечный результат реально работающим в проекте.»

После выполнения пользователь должен иметь возможность запустить приложение и пользоваться новым интерфейсом с существующими данными и существующей логикой.

---

0. ГЛАВНОЕ ОГРАНИЧЕНИЕ

НЕ МЕНЯТЬ БИЗНЕС-ЛОГИКУ

Это самое важное правило задачи.

Редизайн должен быть presentation-layer redesign, а не переписывание приложения.

Запрещено без крайней технической необходимости изменять:

- существующую бизнес-логику;
- правила финансовых расчётов;
- правила определения баланса;
- правила определения доступных средств;
- расчёт защищённых средств;
- статусы финансовых сущностей;
- логику долгов;
- логику обязательств;
- логику целей;
- planning logic;
- AI logic;
- структуру PostgreSQL;
- Drizzle schema;
- API contracts;
- существующие API routes;
- server actions;
- authentication;
- существующие permissions;
- формат хранения денежных значений;
- существующую domain model.

Если текущая бизнес-логика уже выполняет нужный расчёт:

используй её.

Не реализовывай этот расчёт повторно на UI.

---

0.1. НЕЛЬЗЯ «УЛУЧШАТЬ» ПРОЕКТ ЗА РАМКАМИ ЗАДАЧИ

Не проводи попутный architectural refactoring.

Не переписывай:

- API;
- backend;
- database layer;
- auth;
- unrelated components;
- другие страницы;

только потому, что тебе кажется, что их можно сделать лучше.

Не занимайся cleanup всего repository.

Не переименовывай массово существующие сущности.

Не меняй структуру проекта без реальной необходимости.

Если существующий код выглядит неидеально, но работает и не мешает реализации нового UI:

оставь его в покое.

---

0.2. РАЗРЕШЁННЫЕ ИЗМЕНЕНИЯ

Можно изменять и создавать то, что непосредственно необходимо для нового интерфейса:

- React-компоненты;
- page/layout components;
- Tailwind styles;
- presentation helpers;
- UI state;
- client-side interaction state;
- responsive behaviour;
- accessibility markup;
- animation;
- визуальные tokens;
- компоненты календаря;
- Day View;
- navigation presentation;
- loading/error/empty states.

Разрешается создать presentation-layer преобразование:

"CalendarViewModel"

или аналогичный derived model.

Но он должен:

- строиться поверх существующих данных;
- не становиться новым domain layer;
- не создавать новую таблицу;
- не менять API contract;
- не дублировать financial business logic.

---

0.3. СОХРАНЯЙ РАБОЧУЮ ФУНКЦИОНАЛЬНОСТЬ

Перед изменением компонента сначала выясни:

- откуда он получает данные;
- какие действия вызывает;
- какие handlers уже существуют;
- какие URL/routes используются;
- какие server actions/API используются;
- какие состояния уже поддерживаются.

После этого меняй presentation.

Нельзя заменять рабочие элементы декоративными заглушками.

Например, если существующая кнопка:

"Добавить расход"

сейчас реально создаёт расход,

новая версия этой кнопки также должна использовать существующий рабочий flow.

Не создавай fake data вместо существующих данных.

Не hardcode реальные финансовые значения ради красивого screenshot.

Mock data допустимы только в тестовых/демонстрационных сценариях, если проект уже использует такой подход.

0.4. SCOPE ЗАДАЧИ

Основной scope этой итерации:

Главный экран

и непосредственно связанные с ним UX-сценарии:

- Current Money Dashboard;
- календарь месяца;
- Calendar Header;
- CalendarDay;
- смена месяца;
- responsive density;
- маркеры календаря;
- навигация из календаря;
- Day View;
- переход Day → Financial Event;
- возвращение обратно;
- global "+";
- action selector для "+";
- состояния loading/error/empty/offline для этого flow;
- mobile bottom navigation, если она относится к текущему layout.

Не перерабатывай визуально весь Personal Finance OS в этой итерации.

Если переход ведёт на уже существующую страницу долга, обязательства, цели и т. п., достаточно сохранить корректную навигацию на неё.

Не редизайнь эту страницу без необходимости.

---

0.5. СНАЧАЛА ИССЛЕДУЙ ТЕКУЩУЮ РЕАЛИЗАЦИЮ

Не начинай писать новый экран сразу.

Сначала найди минимальный набор файлов, отвечающих за:

- текущую главную страницу;
- календарь;
- получение финансовых данных;
- navigation;
- создание операций;
- используемые UI primitives.

Не сканируй весь repository без необходимости.

Используй progressive discovery.

Принцип:

"entry page → imports → relevant components → relevant data hooks/actions"

а не:

"прочитать весь repository → начать работу".

Это нужно одновременно для:

- экономии токенов;
- снижения риска случайных изменений;
- сохранения существующей архитектуры.

- есть ли визуальная индивидуальность?
- выглядит ли экран как настоящий продукт, а не Dribbble shot?

сделай ещё одну итерацию.

0.13. ДИЗАЙН ДОЛЖЕН ИМЕТЬ СОБСТВЕННЫЙ ХАРАКТЕР

Нужна минимум одна сильная узнаваемая особенность интерфейса.

Она должна вытекать из самого продукта.

В этой версии естественный кандидат:

финансовый календарь как визуальная временная карта состояния денег.

Но не превращай календарь в декоративный gimmick.

Его уникальность должна исходить из:

- структуры;
- финансовой информации;
- состояния дня;
- взаимодействия с Day View.

---

0.14. CURRENT MONEY DASHBOARD

Dashboard не должен выглядеть как отдельная рекламная hero-card.

Он является частью финансового рабочего пространства.

Главный приоритет:

"Доступно сейчас"

Вторичные значения:

- свободно;
- защищено;
- в пути.

Найди способ показать их максимально ясно и компактно.

Не делай четыре одинаковые карточки.

---

0.15. КАЛЕНДАРЬ — ГЛАВНЫЙ ВИЗУАЛЬНЫЙ ОБЪЕКТ

После открытия страницы взгляд должен естественно идти:

"Current money → Calendar".

Не:

"Header → огромная dashboard card → куча widgets → где-то calendar".

Календарю необходимо отдавать основное пространство viewport.

Особенно на mobile.

---

0.16. REAL DATA FIRST

Дизайн должен выдерживать реальные значения.

Проверь минимум:

- "0 ₽"
- "850 ₽"
- "48 320 ₽"
- "126 340 ₽"
- "−48 755 ₽"
- "1 284 550 ₽"

Calendar net:

- "+800"
- "−3.4k"
- "+28k"
- "−125k"
- "+1.2M"

Не изменяй реальный формат хранения денег.

Presentation formatting должен происходить отдельно.

---

0.17. STATES — ОБЯЗАТЕЛЬНАЯ ЧАСТЬ IMPLEMENTATION

Не оставляй edge states «на потом».

Для главного flow должны реально существовать корректные состояния:

- loading;
- initial loading;
- month loading;
- empty month;
- partial data;
- API error;
- retry;
- offline;
- disabled mutations;
- overdue;
- pending income;
- protected deficit;
- no events;
- 5-week month;
- 6-week month.

Не обязательно превращать каждое состояние в отдельный крупный компонент.

Но интерфейс не должен ломаться при их появлении.

---

0.18. ERROR ISOLATION

Ошибка одного участка данных по возможности не должна уничтожать весь главный экран.

Например:

если не загрузился secondary monthly aggregate,

но календарные данные доступны,

покажи календарь.

Не заменяй всю страницу:

"Something went wrong".

Используй локальные recoverable states там, где существующая архитектура позволяет это сделать.

---

0.19. СОХРАНЯЙ URL / NAVIGATION SEMANTICS

Если существующее приложение уже имеет routes для:

- debt;
- obligation;
- goal;
- income;
- expense;

используй их.

Не создавай альтернативный параллельный routing только ради нового дизайна.

Flow должен быть:

"Calendar"

→ "Day"

→ "Event"

→ "existing financial entity"

и обратно.

---

0.20. DAY VIEW

Day View — это следующий уровень информации после календаря.

Он не должен дублировать всю страницу календаря.

Задача:

«объяснить, почему конкретный день выглядит именно так.»

Day View должен использовать реальные данные проекта.

Не делай fake transaction rows.

При tap на существующий объект переход должен работать.

---

0.21. GLOBAL +

Сохрани рабочую существующую логику создания финансовых сущностей.

Новый action selector — это только presentation/navigation layer.

Flow:

"+"

→ выбор типа

→ существующий/new full-page editor

→ существующая mutation logic.

Не переносить mutation/business logic внутрь Action Sheet.

0.25. ФОРМАТ РАБОТЫ

Не ограничивайся рекомендациями.

После этого сразу приступай к работе.

3. выбери наименее инвазивный вариант.

Не переписывай backend ради соответствия дизайну.

---

0.26. DEFINITION OF DONE

Работа считается законченной только если:

- новый главный экран реализован;
- используются реальные данные приложения;
- существующие financial calculations сохранены;
- календарь работает;
- переключение месяцев работает;
- переход в Day View работает;
- возвращение сохраняет контекст;
- global "+" работает;
- существующие mutations продолжают работать;
- состояния loading/error/offline предусмотрены;
- 390×844 выглядит хорошо;
- 375×667 выглядит хорошо;
- 320 px не ломается;
- шестинедельный месяц помещается;
- реальные большие суммы не ломают layout;
- TypeScript не содержит новых ошибок;
- UI визуально проверен после реального рендера;
- после visual review выполнена хотя бы одна polish-итерация.

0.27. КРИТЕРИЙ КАЧЕСТВА

Не оптимизируй работу под:

««Я выполнил пункты ТЗ».»

Оптимизируй под:

««Этот интерфейс можно оставить пользователю как production UI и пользоваться им каждый день».»

Особенно важны:

1. визуальная иерархия;
2. календарь;
3. реальные финансовые данные;
4. компактность;
5. mobile ergonomics;
6. работающая логика;

После этого UI работает с готовым:

YYYY-MM-DD

131. Money Formatting

Создать единый utility.

Например концептуально:

formatMoney(kopecks)

Он принимает integer kopecks.

Не использовать в компонентах самодельные "/100" в десятках мест.

---

132. Compact Money Formatting

Отдельный utility:

formatCompactMoney()

Для календаря.

Например:

"12500000 kopecks"

→

"125k".

Точные значения всегда доступны в detail screen.

149. Acceptance Criteria — главный экран

Главный экран считается реализованным корректно, если:

- календарь является центральным визуальным элементом;
- Dashboard не вытесняет календарь;
- 6-недельный месяц помещается корректно;
- 320 px не ломает layout;
- нет mobile Day Preview;
- tap по дню открывает Day View;
- Dashboard всегда означает текущий момент;
- будущий месяц не подменяет semantics текущего баланса;
- IN_TRANSIT визуально отделён;
- HARD protection визуально понятен;
- большие суммы не ломают ячейки;
- системный Back gesture не конфликтует с календарём.

---

150. Acceptance Criteria — приложение

Редизайн считается готовым только если:

- реализованы все перечисленные разделы;
- каждый экран имеет loading state;
- каждый экран имеет empty state;
- network error не разрушает всё приложение;
- destructive actions подтверждаются;
- forms имеют inline validation;
- touch targets ≥44 px;
- интерфейс работает при 320 px;
- tablet не выглядит растянутой mobile-версией;
- desktop использует sidebar;
- WCAG AA соблюдается;
- API key не раскрывается;
- AI proposals явно обозначены как draft;
- domain statuses сохраняют совместимость;
- API routes не ломаются;
- DB schema не меняется ради UI;
- money calculations продолжают использовать integer kopecks.

---

151. Что не входит в редизайн

Без отдельного требования нельзя:

- менять PostgreSQL schema;
- переписывать domain model;
- менять API contracts;
- внедрять новую offline sync architecture;
- менять financial invariants;
- автоматически перемещать деньги;
- давать AI прямой доступ к выполнению финансовых операций;
- добавлять новые финансовые расчёты только потому, что они красиво выглядят в UI.

---

152. Финальный продуктовый принцип

Personal Finance OS должен ощущаться не как:

Dashboard с календарём внутри.

А как:

финансовый календарь, вокруг которого построена вся система управления деньгами.

Календарь показывает сигнал.

День показывает контекст.

Финансовый объект показывает детали и действия.

План показывает, что делать дальше.

AI помогает принимать решение, но никогда не маскируется под фактически выполненную операцию.

Главная цель интерфейса:

«пользователь за несколько секунд понимает текущее финансовое состояние, видит ближайшее будущее и может перейти от конкретной даты к любому связанному финансовому объекту, не теряя контекст.»
